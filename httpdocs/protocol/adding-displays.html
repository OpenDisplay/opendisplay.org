Adding New Displays Guide

Flex tool — for extending reference firmware, not the core OpenDisplay spec.

Overview

From firmware 3.0 on, OpenDisplay drives every SPI e-paper panel from its configuration, not from a driver compiled into the firmware. The init sequence, the refresh sequence, the waveforms, the BUSY behaviour, the colour codes and the sleep sequence are packets in the device config. No 3.x target links bb_epaper.

So adding a panel means adding an entry to the panel database, not changing firmware. The database lives in Firmware_Unified under panels/. Its generated artefact, panels/generated/drive_presets.json, is what the Toolbox, Home Assistant and py-opendisplay read. The Toolbox writes those packets into the device config when you pick the display.

Need Help?

Ask on the OpenDisplay Discord. Many people have brought up panels before you.

How a panel is described

Four length-prefixed config packets (config minor 6) describe one display. The legacy display packet (32) still carries the pins, the size and the colour scheme.

PacketNameWhat it carries
0xB1display_panelBUSY polarity and timeout, or a fixed delay when BUSY is unusable; the 4-colour code_map; the sleep sequence. Without it a 3.x device refuses to drive the panel.
0xAEdisplay_modeOne drive mode (for example full, fast, partial, colour16): passes, temperature window, waveform slots and the drive sequence. Mode 0 is the default.
0xAFdisplay_lutA waveform at its real length, referenced by a mode's lut_slot.
0xB0display_calibrationMeasured palette of a mode, used by the host for dithering (16-colour BWRY).

The packet layouts are in Firmware_Unified shared/protocol/opendisplay_structs.h and in the Toolbox schema (config.yaml, length_prefixed_types).

Step 1: Is the panel already in the database?

Look up its legacy panel_ic_type in panels/generated/coverage.md. Every panel that 2.x firmware supported has an entry. Each entry has a status:

StatusMeaningIn the Toolbox
glassSeen working on a real panel.Offered.
equivalentConverted from the 2.x driver. Replayed on the host through the real firmware interpreter, the bus traffic matches the 2.x driver byte for byte. Never seen on glass.Offered, marked untested on glass.
blockedThe sequence needs something the firmware interpreter cannot do yet (the entry names it, for example SEQ_MAX).Not selectable for 3.x devices; the reason is shown. Keep such displays on 2.x until it is lifted.

If your panel is listed as equivalent and you have one, test it (Step 5) and report the result: that is how entries become glass.

Step 2: Add a panel to the database

2.1 A panel bb_epaper already drives

Add it to panels/panel_ids.json and run python3 panels/tools/gen_all.py in Firmware_Unified. It captures bb_epaper's bus traffic for the panel, derives the drive packets, replays them through the firmware's interpreter and writes the entry with its status. Nothing is approximated: what cannot be expressed blocks the mode, with the reason.

2.2 A new panel

Write an entry in panels/panels.yaml from the controller datasheet or the vendor sample code: the init and refresh sequence, the waveform if the panel takes one, the BUSY policy, the colour code map and the sleep sequence. panels/README.md describes the format and the sequence language. Give it a new panel_ic_type that no other panel uses.

2.3 Check it

python3 tests/panels/test_panels.py checks the schema, the packet layout, the config size budget (the whole config must fit 3120 bytes on BG22 and 4096 bytes elsewhere) and the replay.

Step 3: Bring it to the website

The Toolbox reads a vendored copy of the database. Refresh it from a Firmware_Unified checkout:

python3 .github/scripts/sync-drive-presets.py /path/to/Firmware_Unified python3 .github/scripts/sync-drive-presets.py /path/to/Firmware_Unified --check # CI: exit 1 when stale

It writes httpdocs/firmware/toolbox/drive-presets.json. Mention the Firmware_Unified commit in the commit message.

Step 4: Add a display preset

Add the display to httpdocs/firmware/toolbox/simple-config-presets.json (displays), with a new id and a new index, and register both in simple-config-id-registry.json. Ids and indexes are permanent once published.

  • panelIcType is the database key. It is still written into the display packet: 3.x firmware treats it as informational, while older clients use it, with color_scheme, to pick colour codes. Keep both accurate.
  • config holds the size, the active area and the colour scheme. The pins come from the board preset.
  • Do not copy drive packets into the preset; the Toolbox takes them from the database.
python3 .github/scripts/validate-simple-config-presets.py node --test tests/

Step 5: Test on a device

  1. Install firmware 3.x on the board (Toolbox; see the upgrade guide).
  2. Set it up with your display. The Toolbox writes the drive packets and reads them back.
  3. Send an image from the BLE Tester and look at the panel. Check every colour for 3- and 4-colour panels: a wrong code_map shows up as swapped yellow and red.
  4. Report what you saw, with the panel's part number, in an issue on Firmware_Unified.

Pin configuration reference (display packet 32)

Field Description Notes
reset_pin Panel reset pin Use 0xFF if not present
busy_pin Panel busy status pin Use 0xFF if not present
dc_pin Data/Command select pin Use 0xFF if not present
cs_pin SPI chip select pin Use 0xFF if not present
data_pin Data out pin (MOSI) Required for SPI communication
clk_pin Clock pin (SCK) Required for SPI communication

Firmware 2.x

Firmware 2.x (OpenDisplay/Firmware, Firmware_Silabs 2.x, Firmware_NRF54 1.x) drives panels through bb_epaper, selected by panel_ic_type in the display packet; it ignores the drive packets. A panel new to 2.x needs a bb_epaper driver and a firmware mapping from panel_ic_type to it. 2.x receives fixes only; new panels go into the 3.x panel database. The Toolbox keeps 2.x devices on this model: it writes no drive packets to them.
